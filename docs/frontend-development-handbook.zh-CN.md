# 前端开发手册

本文档记录 Kairos 前端实现、联调和评审中的公共工程经验。视觉与交互取舍参见[页面设计基准](./page-design-baseline.zh-CN.md)；本文关注如何可靠地实现这些设计。

## 0. 从最小实现开始

Kairos 只有少量页面，不按大型管理后台的假设设计数据层。

- 进入一个页面时加载这个页面需要的数据。
- 当前页面发生操作后，只刷新当前可见且受影响的数据。
- 离开页面后停止它的 Query；返回时由该页面自行重新加载。
- 默认不轮询、不做乐观更新、不维护跨页面的即时一致性。
- 缓存只用于减少短时间重复请求，不承担业务正确性，也不作为资源存在性的依据。
- 不提前实现尚未出现的实时协作需求；需要时优先设计 SSE 等明确的事件通道。

复用应当减少调用方需要知道的细节，而不是建立通用数据同步框架。一个 helper 应对应清楚的页面层级或用户动作，例如刷新主页、刷新当前 WorkItem、刷新当前 Task，而不是同时协调所有页面缓存。

页面数据请求应由页面或紧邻页面的 hook 拥有。根组件只协调路由和顶层弹层，不集中维护所有页面的 Query。按页面拆分应优先移动真实的数据和状态所有权；如果只是把 JSX 机械搬到另一个文件，却没有减少依赖或判断，不视为有效重构。

## 1. 前端展示能力，后端裁定能力

前端不复制需要领域知识才能判断的操作资格，例如 Task 能否认领、拆分、提交或 Review。

- 后端执行上下文返回明确的 capability，例如 `CanDecompose`。
- capability 与对应命令必须复用同一个校验函数，避免“按钮可见但请求被拒绝”或“命令允许但按钮消失”。
- 前端只根据 capability 决定是否展示操作，不从状态、历史、Claim 和身份重新拼装规则。
- 后端仍必须在执行命令时重新校验；capability 是界面提示，不是授权凭证。
- capability 只表达当前身份、当前版本数据下的结果。操作后应刷新上下文，不能长期缓存为本地事实。
- UI 是否采集一个字段，不决定领域命令是否保留该字段。例如 Human UI 可以无原因释放 Claim；Agent Claim 到达 lease deadline 后仍保持 Active，直到 reaper 回收并由后端记录独立的 `expired` 结束原因与 `task.claim_expired` 事件。

复杂的领域判断必须由后端统一完成，例如 Claim 所有权、执行历史、能力组合和状态转换。简单且稳定的展示判断可以交给前端计算，例如 Blackboard 中 `pending && 无 Active Claim` 时显示“跳过”，或 `waiting_children` 时显示“追加子任务”。后端仍必须完整校验所有命令。

纯展示规则也可以留在前端，例如默认展开哪个操作、完成记录是否折叠。判断是否由前端完成，标准不是代码行数，而是规则是否依赖领域不变量、权限或未来可能变化的后端状态。

## 2. 先定义操作矩阵，再实现组件

Task 操作不能按按钮逐个追加。实现前应列出最小操作矩阵：

| 维度 | 需要覆盖的情况 |
| --- | --- |
| Task 状态 | `pending`、`working`、`waiting_children`、`in_review`、终态 |
| 执行者 | human、agent、either |
| 当前身份 | 人、Agent、非执行者 |
| Claim | 无 Claim、自己持有、他人持有、已结束 |
| 上下文 | 加载中、成功、失败、刷新后变化 |
| 操作结果 | 成功、领域冲突、网络失败、重试 |

矩阵中的每个有效组合应明确：展示哪些操作、默认展开哪一个、提交什么命令，以及操作完成后刷新哪些数据。没有先回答这些问题，就不开始写具体表单。

## 3. 一个操作容器，一种交互模式

同一对象上的操作应共享统一的容器和状态模型。

- Task 的完成、释放、无法完成、Review、拆分、追加子任务和跳过都使用同一个 `OperationPanel` 模式。
- 每项操作由“标题、一句说明、表单或确认动作”构成。
- 操作互斥展开，也允许全部收起。
- Review 或规划操作不能因为内容稍复杂就另开页面或叠加浮窗。
- 加载、错误、重试和提交中的状态也属于操作容器，不应由各表单随意实现。
- Workflow 声明预期 Artifact 时，完成表单同时支持上传托管文件和登记外部 URI；上传必须先获得 Artifact ID，再随 Submission 一起提交，不能把本地文件名或临时 Blob URL 当作交付结果。相同文件的失败重试必须复用同一个 Idempotency Key，选择新文件或切换 Claim 时再生成新 Key。

统一外观还不够。组件应共享相同的展开规则、错误呈现、按钮位置、禁用条件和刷新策略。

## 4. 明确组件生命周期和状态边界

表单状态必须属于具体业务对象，而不是偶然复用的面板实例。

- 从 Task A 切换到 Task B 时，A 的结果、失败原因、Review 意见和拆分草稿不能出现在 B 中。
- 详情组件应以稳定业务 ID 作为身份；需要完全隔离状态时，用业务 ID 作为 React `key` 重新挂载。
- 同一 Task 内切换折叠操作时，可以保留尚未提交的输入。
- Mutation 成功后只清理对应表单；失败时保留输入，方便修改和重试。
- URL、Query key 和组件 key 应使用同一组业务标识，避免页面显示对象与缓存对象错位。

评审状态管理时，不能只在一个 Task 内点击。至少要执行“填写 A、切换到 B、再返回 A”的路径。

## 5. 请求状态不能静默降级

依赖远端上下文的操作必须显式处理加载和失败。

- 加载时提供稳定的占位，不让布局突然跳动。
- 加载失败时说明操作暂不可用，展示可理解的错误，并提供重试。
- 失败态应放在所有消费者共有的上层，不能只覆盖 Human 操作而漏掉 Agent 或 Blackboard 操作。
- 不把“请求失败”当成“没有权限”或“没有可用操作”；这三者必须有不同表现。
- Mutation 失败不得关闭详情或清空用户输入。

错误处理的评审单位是数据依赖，而不是某一个组件分支。

## 6. API 集合统一使用空数组

除非 `null` 与空集合具有明确且已记录的不同语义，JSON 集合字段必须返回 `[]`。

- 后端在应用层或传输边界统一规范化集合。
- 前端集合类型声明为数组，不使用 `T[] | null` 扩散防御性判断。
- 可选的单一对象仍可使用 `null`，例如 Active Claim、Parent Task 或某一模式专属的 Context。
- 修改响应结构时，同步更新 HTTP、MCP、前端类型和空集合回归测试。
- 不依赖 `?.map` 掩盖错误契约；类型应帮助我们尽早发现返回值不一致。

## 7. Query 和刷新策略按可见页面设计

每个 Mutation 都应明确当前页面中哪些数据受影响，并通过一个可等待的刷新函数统一处理。

- Task 操作刷新 Task Context 和当前 WorkItem Context。
- WorkItem 层操作只刷新当前 WorkItem Context。
- 主页操作只刷新主页列表和 Attention 聚合结果。
- Query key 必须包含身份和业务 ID；身份变化后不能复用前一个身份的权限上下文。
- capability 与操作数据来自同一个 Task Context Query，避免重复请求和短暂不一致。
- 不用本地猜测修改复杂领域状态。Mutation 成功后，以后端返回或重新读取的状态为准。
- 刷新期间保留稳定界面，避免把短暂的重新加载表现成操作消失。
- Mutation 不负责标记或维护其他页面的缓存。返回主页或进入其他页面时，由目标页面自行加载数据。
- 操作区使用同一个 Task Context 快照中的 Task、Claim 和 capability；WorkItem Context 主要负责列表和整体结构，避免两个 query 的中间状态拼成一个不存在的局面。
- Query 默认不轮询。确有实时协作需求时单独讨论，并优先使用 SSE 等服务端事件让相关 Query 失效，而不是设置全局定时请求。
- 不可见页面或未打开功能所需的 Query 应 disabled，例如 WorkItem 页面不请求主页列表，创建浮窗关闭时不请求 Definitions。
- 聚合页面需要跨多个 WorkItem 的轻量信息时，优先由后端提供聚合接口，避免前端为了一个列表发起 N+1 个 Context 请求。
- 缓存用于加速展示，不能裁决资源是否存在。URL 指向的 WorkItem 或 Task 是否有效，应以对应资源请求的结果为准。

## 8. UI 身份与 API 类型

Kairos Web UI 服务人类使用者。Agent 通过 MCP 或 Skill 工作，前端不保留模拟 Agent transport 的调试分支；确有调试需求时再作为独立工具补充。

- 浏览器身份只采集 Human Actor ID。
- Task 的 `executor` 仍可显示 human、agent 或 either，但这不改变当前 UI 使用者的身份。
- Mutation API 必须使用明确的输入类型，不使用笼统的 `object` 或 `Record<string, unknown>` 绕过编译检查。
- FormData 在组件边界转换为明确的字符串、枚举和数组，再传给 API。

## 9. 验证状态转换，不只检查截图

视觉检查只能证明一个时刻看起来正确，不能证明交互可靠。Task 操作变更至少验证：

1. 正常路径：操作可见、请求正确、成功后状态更新。
2. 身份路径：人、Agent、所有者和非所有者看到正确能力。
3. 负向路径：领域冲突和网络失败有可恢复反馈。
4. 导航路径：切换 Task、关闭再打开、刷新 URL 后状态正确。
5. 生命周期路径：表单不串数据，失败不丢输入，成功只清理相关输入。
6. 契约路径：空集合为 `[]`，可选对象才是 `null`。
7. 一致性路径：UI capability 与实际后端命令接受条件一致。

Blackboard 至少覆盖：pending 的认领/跳过、working 的完成/释放/失败/拆分、waiting_children 的追加子任务、Task Context 失败重试、Mutation 刷新期间防重复提交，以及切换 Task 后表单状态隔离。

完成后运行：

```bash
go test ./...
cd web && npm test && npm run build && npm run lint
git diff --check
```

编译和单元测试通过只是底线。涉及交互状态时，还要按上述矩阵完成真实浏览器路径检查。

## 10. 评审时从共性边界向外检查

发现一个问题后，不只修复当前分支，还应检查同类消费者。

- Human 操作加载失败时，检查 Agent 和规划操作是否使用同一错误边界。
- 一个集合出现 `null` 时，检查同一响应及其他传输层的全部集合。
- 一个操作使用独立浮窗时，检查所有 Task 操作是否遵循统一模式。
- 一个表单切换 Task 后残留时，检查所有局部状态和 Mutation 错误是否同样残留。
- 一个按钮由前端推断资格时，检查其他领域操作是否也维护了重复规则。

Review 的目标不是逐项修补，而是识别产生这类问题的共同结构，并一次收紧边界。

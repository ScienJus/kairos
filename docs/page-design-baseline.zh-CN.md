# 页面设计基准

本文档只定义 Kairos 界面的稳定设计原则，用于设计和评审。页面数据流、状态管理和 API 使用方式见[前端开发手册](./frontend-development-handbook.zh-CN.md)，Task Detail 的结构见 [Task Detail 架构](./task-detail-architecture.zh-CN.md)。

## 1. 设计目标

Kairos 应让人快速理解当前局面，专注推进一件工作，并在离开后可靠恢复。它不是以信息密度和管理效率为首要目标的后台系统。

- 保留留白，不用无关指标填满页面。
- 使用人的意图描述动作，避免暴露内部数据操作。
- 只让当前决策需要的信息获得高视觉权重。
- 动效只解释层级变化和操作结果，不持续吸引注意力。

## 2. 页面层级

界面只有三个主要层级：

1. 主页选择 WorkItem。
2. WorkItem 页面解释目标和执行局面。
3. Task Detail 查看或处理单个 Task。

每个可恢复位置必须映射到 URL，刷新、前进和后退都应保持语义。打开 Task Detail 不应挤压底层布局；关闭后应回到原来的位置。不要为没有独立心智模型的内容新增页面。

## 3. 渐进披露

首屏只显示当前判断所需的信息：

- WorkItem：标题、目标、状态和进入动作。
- Brief：Acceptance Criteria、Context 和 Constraints。
- Task 列表：名称、层级和状态。
- Task Detail：描述、执行者、Claim、Submission、Review 和 Failure History。

搜索、筛选、技术 ID 和时间戳只在确有使用需求时出现。渐进披露不是隐藏关键信息，而是让信息在需要时出现。

## 4. 主页

主页把工作分成两个区域：

- `open` WorkItem 是当前工作，以宽松卡片呈现。
- `completed`、`cancelled` 和 `failed` WorkItem 是历史，以结束时间倒序的 Timeline 呈现。

Task 失败不等于 WorkItem 结束。两个区域使用页面自然滚动，不建立彼此独立的滚动容器。

## 5. WorkItem 页面

页面以目标和执行局面为主角：

- Blackboard 使用有层级关系的 Checklist，规划动作自然地附着在 WorkItem 或 Task 上。
- Workflow 使用 Flow Graph，优先表达分叉、合并、循环和当前执行位置。
- 状态帮助理解局面，不演变成统计仪表盘。
- 与当前 WorkItem 无关的动作不持续占据页面。

Blackboard 不要求人维护 Role、建议关系或复杂依赖。Tags 可用于分类、检索和 Agent 上下文，但不表达权限或依赖。

## 6. Task Detail

Task Detail 是“拿起一张工作单”的独立层，而不是常驻第三栏。

- 打开和关闭不改变底层布局；支持明确的关闭入口、点击外部和 `Esc`。
- 桌面端可使用较宽的覆盖层，移动端接近全屏。
- 信息按任务进展组织，不按数据库字段排列。
- 可执行动作使用同一个互斥折叠组；切换动作不丢失未提交输入。
- 系统根据当前状态和真实 capability 默认展开最合适的动作。

## 7. 视觉与交互语言

- 使用浅色、低饱和配色；主蓝色为 `#336774`。
- 色彩表达层级、状态和动作，不做大面积装饰。
- 使用柔和边界和轻微阴影表达可操作物体，避免所有区域都卡片化。
- 等宽字体只用于确需区分的技术内容。
- 避免网格背景、发光描边、密集刻度和仪器式装饰。
- 空状态可以安静，不用长说明填补空间。

Workflow Editor 的未连接 Task 使用紧凑布局；新增节点只聚焦新节点，不重新缩放整张图；用户手动摆放的节点不因自动布局跳回。

## 8. 一致性

同级页面标题使用相同起点，切换时不漂移。内容宽度可随任务变化，移动端仍保持一致边距。

界面支持中文和英文：

- locale 同时决定文案、状态名和日期时间格式。
- 语言选择持久保存。
- 用户和 Agent 写入的业务内容保持原文。
- 新增可见文案时同步补充两种语言。

## 9. 评审清单

每次页面变更至少确认：

1. 使用者能否立即知道当前要关注什么？
2. 是否同时展示了本可分层呈现的信息？
3. 是否加入了没有明确用途的指标、筛选器或说明？
4. 主要动作是否属于当前页面层级？
5. 内容较少时是否允许留白？
6. 打开详情是否会移动底层布局或丢失位置？
7. 是否产生了不必要的内部滚动？
8. 状态是否清楚但不过度抢眼？
9. 文案表达的是人的意图还是系统操作？
10. 长时间使用后是否仍安静、易读？

与本基准冲突的设计应先说明新的使用场景和必要性，再修改基准。

# 页面设计基准

本文档记录 Kairos 人机界面的设计共识。它用于指导后续页面设计、实现和评审。

具体的前端实现、状态管理、API 契约和验证要求参见[前端开发手册](./frontend-development-handbook.zh-CN.md)。

Kairos 的界面不以信息吞吐量或管理效率为首要目标。它应当让人愿意停留、容易理解当前局面，并能没有负担地与 Agent 一起推进工作。

## 1. 不是管理后台

Kairos 不应被设计成仪表盘、控制台或传统管理后台。

- 不使用密集的多栏布局承载所有信息。
- 不让计数、ID、时间戳、筛选器和系统状态长期占据注意力。
- 不为了显得专业而加入无实际用途的指标、装饰和技术术语。
- 不要求使用者先理解系统的数据结构，才能知道下一步该做什么。

界面应更接近一个安静的经营空间：使用者一次拿起一件工作，观察当前局面，做出一个动作，再把它放下。

## 2. 一次只关注一个层级

页面应通过空间和交互区分不同层级，而不是同时展示全部层级。

- 主页用于选择 WorkItem。
- WorkItem 页面用于理解目标和当前执行局面。
- Task Detail 用于查看或处理单个 Task。

进入 WorkItem 后，主页内容应退出视野。打开 Task 后，详情应作为独立层出现，不挤压或改变底层布局。关闭详情后，使用者应回到打开前的位置。

每个页面层级和可恢复的工作位置都必须映射到 URL。刷新页面应恢复当前 WorkItem、Task Detail 或主页视角；浏览器前进与后退应保持可用。

Kairos 预计只需要少量页面。不要为了建立完整导航体系而拆分没有独立心智模型的页面。

## 3. 信息按需出现

首屏只呈现当前决策所需的信息。

- WorkItem 首先展示标题、目标和当前状态。
- Acceptance Criteria、Context 和 Constraints 收纳在可展开的 Brief 中。
- Task 列表首先展示名称、层级和状态。
- Description、Executor、Claim、Submission、Review 和 Failure History 在 Task Detail 中展示。
- 搜索和筛选只在数据规模确实需要时出现，不应成为页面的默认骨架。

渐进披露不是隐藏重要信息，而是让信息在使用者需要它时出现。

## 4. 主页：当前工作与工作历史

主页区分两类 WorkItem，它们具有不同的含义和视觉表达。

### 未完成的工作是卡片

未完成的 WorkItem 是当前可以进入、仍需照看的工作空间，因此使用卡片呈现。

- `open` 的 WorkItem 属于当前工作。
- Task 的执行失败不会使 WorkItem 离开当前工作；可继续处理的 WorkItem 保持 `open`。
- 卡片强调标题、目标、状态和进入动作。
- 卡片应有足够的尺寸和留白，不压缩成表格行。
- 卡片数量较少时，应允许页面保留空白，而不是用其他信息填满空间。

### 已完成的工作是 Timeline

生命周期已经结束的 WorkItem 是历史，而不是另一个待管理列表，因此使用 Timeline 呈现。

- `completed`、`cancelled` 和 `failed` 的 WorkItem 进入 Timeline。
- Timeline 按结束时间倒序排列，最近结束的工作在前。
- 每一项展示标题、最终状态、开始时间和结束时间。
- Timeline 的视觉权重低于当前工作，但仍可进入查看完整内容。
- Timeline 自然排列在当前工作之后，不使用向上展开的折叠面板。

主页使用整个页面自然滚动。当前工作和 Timeline 不各自创建内部滚动区域。

## 5. WorkItem 的执行局面

WorkItem 页面以目标和执行局面为主角，不重复主页上的管理信息。

- Blackboard 渲染为具有层级关系的 Checklist。
- Workflow 渲染为 Flow Graph。
- Blackboard 的父子关系应通过缩进和必要的连接提示清晰表达。
- Workflow 应优先表达分叉、合并、循环和当前执行位置，而不是展示节点元数据。
- 状态用于帮助理解局面，不应演变成一组占据页面的统计指标。

页面中的主要动作应与当前工作直接相关。进入 WorkItem 后，不持续展示“新建其他工作”等无关动作。

### Blackboard 的规划

Blackboard 的规划是对当前 Checklist 的自然补充，不使用独立图编辑器或全局规划工具栏。

- WorkItem 层只负责添加顶层 Task，以及在空 Blackboard 中选择直接完成。
- 已认领的 Task 可以在 Task Detail 中拆分为子任务；等待子任务的父 Task 可以继续追加子任务。
- 未认领的待处理 Task 可以由人说明原因后跳过。这类干预入口保持低强调。
- 规划操作使用 Task Detail 既有的操作区域，不打开嵌套浮窗，也不进入新的规划页面。
- Blackboard 不主动设置或展示 Role。Task 可以保留 Tags，用于分类、检索以及为 Agent 提供上下文，但 Tags 不表达执行权限或依赖关系。
- 不要求人维护任务之间的建议关系或复杂依赖；确有稳定使用需求后再引入相应能力。

## 6. Task Detail 是拿起一张工作单

Task Detail 是独立层级，而不是常驻的第三栏。

- 从 Checklist 或 Flow Graph 选择 Task 时打开。
- 打开和关闭不应引起底层页面抖动或重排。
- 支持明确的关闭按钮、点击外部关闭和 `Esc` 关闭。
- 详情可以比普通侧栏更宽，保证描述、结果和 Review 内容易于阅读。
- 移动端使用接近全屏的独立层。

详情中的信息仍应按任务进展组织，而不是按数据库字段排列。

Task 的可执行动作使用同一个互斥折叠组。系统根据当前状态和实际可用操作默认展开最合适的一项；再次选择当前操作可以将全部表单收起。使用者选择完成、暂时放下、无法完成、Review、拆分或跳过等另一个动作时，当前表单自动收起。多个操作表单不应同时占据详情空间，切换操作也不应丢失尚未提交的输入。

## 7. 交互应自然、有节奏

界面文案和反馈应描述人的动作，而不是系统操作。

- 使用“打开工作空间”“放下当前工作”等自然表达。
- 避免“进入详情页”“加载记录”“执行管理”等后台式用语。
- 动效只用于表达层级变化和操作结果，时间短、幅度小。
- Hover、选中、完成和等待状态应能被感知，但不闪烁、不发光、不持续吸引注意力。
- 空状态允许保持安静，不需要用大量说明填补空白。
- Workflow Editor 的未连接 Task 使用紧凑待连接布局；新增后只聚焦新节点，不重新缩放整张图。用户手动拖动过的节点不因后续连线或自动布局而跳回。

交互可以借鉴经营类游戏的舒适节奏，但不照搬游戏化积分、奖励、装饰或音效。目标是让操作有连续感，而不是让工作变成游戏。

## 8. 视觉语言

整体视觉应安静、柔和、清晰。

- 使用浅色界面，不提供以深色仪器面板为基础的默认主题。
- 以 `#336774` 为主要蓝色，搭配低饱和的传统色系。
- 色彩主要用于层级、状态和动作，不用于大面积装饰。
- 保留充足留白，允许页面在内容较少时显得空。
- 使用柔和边界和轻微阴影表达可操作物体，避免每个区域都成为卡片。
- 字体以易读为先；等宽字体仅用于真正需要区分的技术内容。
- 避免网格背景、发光描边、密集刻度和仪器式装饰。

## 9. 设计评审清单

新增或修改页面时，至少检查以下问题：

1. 使用者进入页面后，是否能立即知道当前只需要关注什么？
2. 页面是否同时展示了本可分层呈现的信息？
3. 是否存在只为显得完整而加入的指标、筛选器、标签或说明？
4. 主要动作是否属于当前页面层级？
5. 内容较少时，是否允许留白，而不是主动填满页面？
6. 打开详情是否会使底层布局移动或丢失位置？
7. 页面是否产生了不必要的内部滚动区域？
8. 状态表达是否清楚但不过度抢眼？
9. 文案描述的是人的意图，还是系统的数据操作？
10. 使用一段时间后，界面是否仍然安静、不容易疲劳？

当设计选择与本基准冲突时，应先说明新的使用场景和必要性，再决定是否修改基准。

## 10. 语言一致性

Kairos 提供中文和英文两套界面语言。

- 界面文案、状态名称、日期和时间格式必须由同一个 locale 决定，不能跟随浏览器默认格式产生中英混排。
- 语言选择应被持久保存，刷新页面后保持不变。
- WorkItem、Task、Submission 和 Review 中由人或 Agent 写入的内容保持原文，不由界面自动翻译。
- 新增可见文案时必须同时补充中文和英文词条。
